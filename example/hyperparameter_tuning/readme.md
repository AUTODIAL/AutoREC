# Full-budget hyperparameter tuning

This example uses [Optuna](https://optuna.org/) and Slurm to tune AutoREC. Run
`runner.py` on a login node. It proposes candidates in synchronous batches, submits one
Slurm training job per candidate, waits for the batch, and gives Optuna one final score per
candidate.

Every candidate trains for `agent.num_trials` from `base_config.yaml` (10,000 trials by
default). There is no early pruning or promotion. Training jobs save complete checkpoints
every 1,000 trials by default, so an interrupted candidate can resume instead of starting
again.

## Data and objective

The included `data/` directory contains three processed datasets:

- `training_dataset.pkl` supplies RL interactions and the learning-curve component of the
  score.
- `validation_dataset.pkl` supplies the success-rate and exact-circuit components.
- `test_dataset.pkl` is reserved for assessment after hyperparameter selection and is not
  loaded by the tuning workflow.

`tuning_utils.compute_score` averages three components: mean episodic cumulative reward over
the most recent 1,000 training episodes, validation success rate, and validation
exact-circuit rate. Because tuning consults the validation set, do not report it as an
unbiased test result.

Paths in `base_config.yaml` are relative to the calculation working directory. Generated
Slurm scripts change to the directory containing `main_factory.py`, so the example remains
self-contained when the complete `example/hyperparameter_tuning/` directory is copied to a
shared HPC location.

## Cluster setup

Install the example dependencies:

```bash
pip install -r requirements.txt
```

Review these cluster-specific values before running:

1. `MODULE_SAVELIST_NAME` and `PYTHON_ENV_PATH` near the top of `tuning_utils.py`.
2. The account, node constraint, time, CPU, and memory directives generated by
   `write_job_script`.
3. Shared-storage paths: the login node and compute nodes must see the example and results
   directories at the same absolute paths.
4. Availability of `sbatch` and `sacct` on the login node.

Checkpoint continuation has a strict deterministic CPU runtime contract. Generated jobs
disable GPUs, fix numerical thread counts, and use deterministic TensorFlow operations. A
checkpoint must be restored with compatible AutoREC source and numerical-library/runtime
metadata. See `docs/checkpointing.md` for the complete contract.

## Run from the login node

From `example/hyperparameter_tuning/`, run:

```bash
python runner.py \
  --target-dir ./hyperparameter_tuning \
  --base-config ./base_config.yaml \
  --search-space ./search_space.yaml \
  --num-initial 5 \
  --num-iterations 10 \
  --batch-size 5 \
  --checkpoint-every 1000
```

The baseline configuration is evaluated first. The remaining initial candidates run in the
first batch, followed by `num-iterations - 1` batches of `batch-size` candidates. Run
`python runner.py --help` for the argument reference.

A temporary `sacct` failure is retried for up to one hour. A job is accepted only when Slurm
reports both the `COMPLETED` state and exit code `0:0`.

Do not submit `runner.py` as a Slurm job. It is a lightweight login-node orchestrator that
submits and monitors the compute-intensive child jobs.

## Recover an interrupted candidate

Each generated candidate job invokes `main_factory.py`. Before training, the worker validates
the checkpoint series in that candidate's `checkpoints/` directory. It restores the latest
complete checkpoint and trains only the remaining trials needed to reach the fixed
`agent.num_trials` target. It then evaluates the final agent on the validation dataset.

If a child job fails or is cancelled:

1. Confirm that no earlier copy of that candidate job is still running.
2. Fix the external cause if necessary (for example, wall time or node failure).
3. Rerun the same `python runner.py ...` command with the same arguments and files.

The deterministic Optuna setup reconstructs the same preceding batches. Completed candidates
are skipped. An incomplete candidate is submitted again, and its worker resumes from its
latest valid checkpoint. Corrupt, incompatible, or mixed checkpoint series fail clearly
instead of silently restarting.

`main_factory.py` can also be run manually for one generated configuration:

```bash
python main_factory.py \
  --config hyperparameter_tuning/configs/config_0001.yaml \
  --checkpoint-every 1000
```

The worker is idempotent after both final checkpoint and evaluation outputs exist.

## Outputs

Each unique configuration has a stable ID:

```text
hyperparameter_tuning/
├── configs/
│   ├── config_0000.yaml
│   └── config_0001.yaml
├── run_0000/
│   ├── checkpoints/
│   │   ├── trial-00001000/
│   │   ├── ...
│   │   └── trial-00010000/
│   ├── dqn_model.keras
│   ├── eval_results.pkl
│   ├── eval_results.csv
│   ├── statistical_analysis.pkl
│   ├── models.tar.gz
│   └── fit_plots.tar.gz
├── candidate_scores.csv
├── optuna_trials.csv
├── optimization_history.png
└── param_importances.png
```

`candidate_scores.csv` reports the total objective and its three components for every
candidate. `optuna_trials.csv` contains the Optuna trial table. Intermediate model and fit
plot directories are archived after successful jobs to reduce file counts; checkpoint
directories remain unpacked so interrupted calculations can resume.

Hyperparameter tuning is expensive and does not establish generalization. Record the search
space and selection procedure, then use the held-out test data for the final assessment.
